## 3. 关键数据流

### 3.1 普通 Bot 文件 / 相册

```text
Telegram update
 → telegramBot.ts 认证/限流
 → telegramUpload.handleFileUpload
 → 固化 storage target + 解析 path rule
 → admitOrdinaryTransferTask (transfer_tasks)
 → DownloadTaskQueue
 → GramJS 下载到 /data 临时文件
 → storage operation lease
 → provider.saveFile
 → files 索引
 → 任务结算 / 失败补偿 / 回执
```

**不变量：** provider、account ID、folder 必须在 admission 时固化；外部对象与 `files` 索引不能只成功一边。

### 3.2 频道日期/标签/订阅

```text
Bot 向导/命令
 → resolve source + allowlist
 → telegram_background_jobs
 → 分段扫描
 → telegram_download_items
 → child claim + lease token + heartbeat
 → telegramUpload.downloadTelegramChannelRange
 → telegram_write_reconciliations journal
 → provider + files index
 → child settlement
 → parent final CAS
 → 订阅 cursor 单调推进（仅 subscription）
```

**不变量：** 旧 lease worker 不得结算新 lease；失败边界之前才可推进订阅 cursor；取消和暂停语义不同。

### 3.3 yt-dlp

```text
/ytdlp URL
 → public HTTP URL 校验
 → 固化 storage target
 → transfer_tasks(ytdlp)
 → PersistentYtDlpQueue
 → claim generation + lease
 → spawn yt-dlp（参数数组 + '--'）
 → 选择主输出文件
 → ytdlp_write_reconciliations
 → provider + files index
 → settle / notify / cleanup
```

### 3.4 Web 上传

```text
React UploadZone
 → 小文件 XHR / 大文件 chunk protocol
 → target snapshot
 → chunk_upload_sessions + chunk metadata
 → completion CAS/heartbeat
 → provider + files index + compensation
 → TasksPage / recovered upload UI
```

## 4. 不可破坏的不变量

开发任何 Bot 新功能前必须阅读并保留：

1. **存储目标快照**：任务提交后不随全局 storage switch 改变。
2. **Storage account lease**：有外部副作用的操作持有租约，账户删除必须阻塞。
3. **Child lease/generation**：旧 worker 不能结算或覆盖新执行。
4. **Write-ahead reconciliation**：外部对象和 DB 索引不确定时留下持久证据。
5. **Pause vs cancel**：暂停阻止新 claim，活动文件可完成；取消才硬中断/补偿。
6. **危险操作确认**：绑定 actor/session、action、object、chat/message、TTL、一次消费。
7. **订阅 cursor**：只能在 parent finalization 同一事务内单调推进。
8. **Cookie auth**：Web 使用 HttpOnly cookie，不把 token 放回 localStorage。
9. **Secrets**：token/session/凭证不写日志、不回显、不进入 Bot 文本。
10. **当前工作树**：不把用户已有删除混入修复提交。

相关回归测试已经覆盖很多协议；不要因为“代码复杂”而绕过服务直接写 SQL/provider。


### 6.2 每个缺陷遵循 RED → GREEN → REFACTOR

以 target snapshot 为例：

1. 在 `telegramBatchConfirmation.test.ts` 写能真实失败的行为测试。
2. focused 运行，确认测试因“快照被 B 覆盖”失败。
3. 最小修改 `createJob` 接口，去掉第二次读取 active target。
4. focused test 变绿。
5. 运行所有相关测试 + 全量 suite。
6. 独立 reviewer 检查 spec compliance 和 code quality。
7. 一个问题一个提交。

### 6.3 推荐提交拆分

```text

fix(bot): validate Telegram date ranges strictly
fix(bot): bind interaction state to chat with TTL
fix(auth): reconcile Telegram allowlist and authenticated cache
```

## 9. 数据库与迁移交接

### 9.1 当前迁移机制

- 新 Postgres volume 先执行根 `init.sql`。
- Backend 启动后读取打包进镜像的 `dist/schema.sql`，逐句执行 `CREATE IF NOT EXISTS` / `ALTER`。
- `backend/src/db/index.ts:51-149` 是实际升级路径。
- 当前没有 migration version ledger；schema 变更是累计幂等 SQL。

### 9.2 增加表/列的安全步骤

1. 先写 migration contract test。
2. 只做向后兼容 expand：nullable/default 列、新表、新索引。
3. 在代码里兼容旧值/空值。
4. 用生产备份的隔离恢复副本演练启动。
5. 部署新 backend，观察 backfill/锁时间。
6. 后续版本才做 contract（删除旧列/约束），不要同版完成。
7. 同步 canonical schema 和首装路径，最终消除双源。

### 9.3 Bot 新功能建议表

- `telegram_interaction_states`：仅在确需跨重启向导时；否则有 TTL 内存 store 即可，YAGNI。
- `telegram_target_states`：chat/user + mode(next/session) + provider/account + expiry。
- `telegram_notification_preferences`：user/chat + timezone + quiet hours + event flags。
- 订阅表增加 target mode/provider/account（如实施 fixed/follow-global）。

所有 account foreign key 都要考虑 `ON DELETE` 语义和 storage account deletion reference check。

4. 设置：


5. 运行协调备份（会停 backend）：


6. 校验备份：


7. 保存旧镜像 digest 和当前 Compose config。

### 10.2 构建镜像

不要继续用与包版本不一致的 `v2.0.0` 标签。示例：


确保 `.env` 中 `IMAGE_VERSION` 与要部署的一致；`VITE_API_URL` 是 build-time 值，修改后必须重建 frontend。


## 11. 回滚步骤

### 11.1 代码/镜像回滚

前提：schema 变更保持向后兼容。

1. 记录失败时间和 request/operation ID。
2. 停止新的功能入口（feature flag 或关闭 Bot required feature）。
3. 把 `IMAGE_VERSION` 改回已记录的旧版本/digest。
4. 只重建/recreate backend/frontend，不删除卷：

```bash
docker compose up -d --no-deps --force-recreate backend frontend
```

5. 验证 `/readyz`、旧前端 asset、Bot 基础命令。

### 11.2 数据回滚

只有以下情况才恢复 DB/文件卷：

- schema/data migration 不可向后读取；
- 已确认写入损坏；
- 运维负责人批准维护窗口。

恢复必须在隔离环境先验证，且数据库 dump 与 `/data` 必须来自同一个 `backend-stopped` 备份目录。**绝不执行 `docker compose down -v`。**

### 11.3 外部存储副作用

数据库回滚不会自动回滚云端对象。先查：

- `telegram_write_reconciliations`
- `ytdlp_write_reconciliations`
- `chunk_upload_reconciliations`
- `storage_account_leases`

待对账记录不为 0 时，不要盲目重试/删除；按 provider/object path/file ID 逐条核验。

## 12. 监控与告警建议

### 必需探针

- `/livez`：进程。
- `/readyz`：DB、schema、storage、security。
- 新增 Bot component health：连接状态、最近 update、重连次数、last error。
- 用户账号 client health。

### 数据库告警查询（只读）

```sql
SELECT COUNT(*) FROM telegram_write_reconciliations WHERE status='pending';
SELECT COUNT(*) FROM ytdlp_write_reconciliations WHERE status='pending';
SELECT COUNT(*) FROM chunk_upload_reconciliations WHERE status='pending';
SELECT COUNT(*) FROM storage_account_leases WHERE released_at IS NULL AND expires_at < NOW();
SELECT status, COUNT(*) FROM telegram_background_jobs GROUP BY status;
SELECT status, COUNT(*) FROM transfer_tasks GROUP BY status;
```

建议告警：

- pending reconciliation > 0 持续 10 分钟。
- expired unreleased lease > 0。
- Bot 非 ready 持续 5 分钟。
- 订阅连续失败 N 次。
- 临时磁盘低于水位。
- backend 容器重启循环。
- npm/镜像扫描出现 high/critical。
